# HiLabs Care Workbench

A static, synthetic-data MVP prototype for a health-plan RN case manager. It focuses on post-discharge and transitions-of-care work: reviewing a prioritized queue, assembling a source-aware member picture, planning outreach, and documenting work with human confirmation.

> **Not for clinical use. Synthetic data only. No real PHI.** This project has no backend, production authentication, or external API calls.

## Run locally

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). The root route redirects to `/queue`.

## Validate

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Export the spreadsheet annex from the same validated seed records:

```bash
npm run export:annex
```

The script writes `data/synthetic-annex.xlsx` with a summary sheet and a sheet for each of the 16 data domains. The Data and Sources screen also provides a browser download.

## Deploy to Vercel

The app requires no environment variables:

```bash
vercel
vercel --prod
```

The project uses Next.js static export (`output: "export"`), so Vercel serves prebuilt files and does not run application server endpoints. For Git-based deployments, import the repository and keep the build output as `out`. Do not connect real member data to this prototype.

## Architecture

```text
Next.js App Router
  ├─ (workbench) routes: queue, member, outreach, documentation, impact, data, scope
  ├─ components: navigation shell, accessible primitives, workflow screens
  ├─ data/seed.ts + data/datasets.ts: typed synthetic records and source catalogue
  ├─ lib/repository.ts: replaceable local data access boundary
  ├─ lib/engines.ts: pure scoring, freshness, confidence and fill-gap calculations
  ├─ config/workbench.ts: scenario time, freshness thresholds, score weights and action rules
  └─ Zustand: in-session overrides, decisions, outreach and documentation audit entries
```

The only green semantic color is `#15803D`, used sparingly for confirmed or complete states. Scores, freshness windows and impact estimates are illustrative, not clinically validated.

## Integrations and limitations

- The 16 data sources are represented as local, typed synthetic records. No plan, pharmacy, EHR, HIE, provider, UM or messaging system is connected.
- Five detailed scenario members and 43 lightweight cases represent the 48-member caseload.
- The priority model and next-action rules are examples for discussion, not validated clinical guidance.
- AI-labeled documentation is generated by deterministic local templates. No model or external service is called. A nurse must review and confirm drafts.
- Zustand audit entries exist only in the current browser session. They are not durable and do not meet production audit or compliance requirements.
- Production use would require clinical governance, validated data matching, authentication, authorization, secure storage, accessibility testing and integration agreements.
- `npm audit --omit=dev` reports advisories for the required Next.js 14 and SheetJS packages. Next.js 14 is retained to match the case specification, and SheetJS is used only to generate an export. Static hosting avoids exposing a Next.js application server, but these versions should be reassessed before any production use.
